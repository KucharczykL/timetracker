# CLEAN-02: Lessons Learned (Abandoned Approach)

**Date:** 2026-09-10  
**Status:** Resolved — new spec written at `docs/superpowers/specs/2026-09-10-cleaning-02-remove-playevent-and-gamestatuschange.md`

**New approach:** Migration-first design with manual migration that removes FK constraints before dropping tables.

## What Went Wrong

### 1. Wrong Order of Operations
The original approach was: **delete code → create migration → fix tests**. This is backwards. The correct order is: **design migration sequence → verify migration path works in isolation → then delete code**.

### 2. Migration Strategy Was an Afterthought
The migration was auto-generated by Django after deleting model classes from `models.py`. This meant:
- The migration depended on `0048_playthrough_start_repair` (which was already elided to a no-op)
- Django's migration auto-detection didn't account for the complex FK constraint chain
- The migration sequence created an inconsistent state during test database setup

### 3. Test Database Flush Failure
The root cause of 862 test errors: Django's test database flush sequence tries to truncate `games_playevent` before migration 0050 drops it. The table has FK constraints to `games_game` that prevent truncation. This is a **migration integrity issue**, not a test issue.

### 4. Whack-a-Mole on Tests
Fixing individual test failures (76 failed, 5142 passed, 862 errors) was masking the underlying problem. Every test fix was a band-aid on a broken foundation.

## What Worked Well

### 1. Adversarial Review
The adversarial review identified 10 factual errors in the plan (line numbers, missing test references, etc.) and those were committed. This saved significant rework.

### 2. Code Changes Were Mostly Correct
The actual code refactoring (removing PlayEvent/GameStatusChange references from cross-cutting modules, updating tests) was done correctly. The problem was the migration strategy, not the code changes.

### 3. Migration Inlining for Historical Migrations
Inlining `playergame.py` backfill into migration `0033` and converting `0045`/`0048` to no-ops was the right approach for historical migrations that depend on deleted modules.

## Key Insights for Re-Planning

### 1. Migration-First Design
Before deleting any model classes:
1. Map all FK constraints involving `PlayEvent` and `GameStatusChange`
2. Design a migration sequence that eliminates constraints BEFORE dropping tables
3. Verify the migration path works in isolation (create DB, apply migrations, flush, recreate)
4. Only then delete model classes

### 2. FK Constraint Chain
`PlayEvent` has FK to `Game`. During test database flush:
1. Django tries to truncate all tables
2. `games_playevent` can't be truncated because FK constraints exist
3. Migration 0050 drops the table but the flush happens before/during migration application

### 3. Proper Migration Sequence Should Be:
```
0048_playthrough_start_repair (elided no-op, already applied)
0049_remove_playevent_game_fk    -- Remove FK from PlayEvent to Game
0050_drop_playevent_table        -- Drop PlayEvent table
0051_drop_gamestatuschange_table -- Drop GameStatusChange table
```

### 4. Test Database Setup
Django's test database creation applies migrations sequentially. The issue is that the flush happens AFTER all migrations are applied but the auto-generated migration 0050 tries to delete the table which may have residual constraints.

### 5. Content Type Cleanup
Django's `DeleteModel` operation automatically clears ContentType entries. This should work fine if the table is properly dropped.

## Questions to Answer Before Re-Planning

1. What FK constraints exist on `games_playevent` and `games_gamestatuschange`?
2. Are there any reverse FKs from other models to `PlayEvent` or `GameStatusChange`?
3. What does `python manage.py showmigrations --plan` show for the migration sequence?
4. Can we verify the migration path works in isolation before deleting models?
5. Do we need explicit `ON DELETE CASCADE` handling for any FK chains?
